Investigating whether gitlore should support a GLOBAL/organizational memory tier alongside its per-project memory. Motivation: David has ~16 sibling repos each with a gitlore `memory/` submodule; `user` + CC-platform `reference` + portable `feedback` memories are trapped and duplicated per-repo, while `project` memories are correctly per-repo.

**Conclusion so far:** a flat merge-everything store is WRONG — it blows the ~200-line always-loaded `MEMORY.md` budget and loads 15 irrelevant projects every session. Right shape is **two-tier**: a global tier (user + CC-platform reference + portable feedback) loaded everywhere, plus per-project tiers staying local. This aligns with a structure Anthropic ALREADY ships — the `team/` subdir + combined index (see [[cc-memory-retrieval-agentic]]). **Design principle: keep Anthropic's memory structure, upgrade only gitlore's GENERATION step — that structure is Anthropic's surface.**

**Load-bearing facts.** Retrieval is agentic (≤5 selective attach), so a large global tier costs little context IF surfaced on-selection rather than bulk-loaded. gitlore today: flat memory submodule, hand-edited `MEMORY.md` (NO generation step anywhere), write path is a uniform `git add -A` (`scripts/lib/resolve.sh:158-161`) with ZERO per-file/per-type routing. `docs/design.md:637` already rejected a global `userSettings` `autoMemoryDirectory` (all projects → one repo). NOTE: the early "write-routing = a classifier" framing was SUPERSEDED during design — routing is the agent picking a directory (see converged design below), no content classifier.

**Experiment DONE (2026-07-14) — both unknowns resolved, the clean two-tier design is confirmed viable** (probe details in [[cc-memory-retrieval-agentic]]; protocol was `~/.claude/plans/go-precious-crystal.md`, sentinel-introspection via `claude --print --settings autoMemoryDirectory=<scratch>`, no real-memory contact):
- Retrieval attaches file BODIES on-selection under `--print` (mechanism fires; not "never read").
- **U1:** both the `MEMORY.md` one-liner AND the per-file `description:` frontmatter feed the classifier — but the index line is the CANONICAL one (always-loaded + the reliable lever); see DRIFT FINDING below.
- **U2a:** a `team/`-style subdir IS enumerated natively (100% for indexed subdir files); depth ≥2 works too.
- **U2b:** subdir/`team/` bodies do NOT bulk-load — the always-loaded footprint is the `MEMORY.md` index blob only. A global tier of N files costs N index one-liners, NOT N bodies. Near-free at baseline as long as the index stays under ~200 lines.
- **Reliability:** indexed files retrieve 100%; an unindexed pure-frontmatter file retrieved 75%. → the generation step MUST emit `MEMORY.md` pointers for global files, not lean on frontmatter enumeration alone.

**CONVERGED DESIGN — captured as D17 in `docs/design.md` (design only; not yet implemented or planned).** Generalized from "two-tier" to **N named tiers**:
- **Materialization:** each tier (`memory/lore` global, `memory/ddaanet` org, …; names configurable) is a **nested git submodule** inside the project memory submodule, reusing the existing init / FR11 gate / push-lockstep framework. `autoMemoryDirectory` is single-path, so tier content is physically present as nested checkouts under it.
- **Routing = agent picks the directory**, guided by an addition to the standing SessionStart `additionalContext` (D12 block): portable → `memory/<tier>/`, project → `memory/`. No content classifier — the directory *is* the tier *is* the submodule; the FR11 gate commits whichever submodule the file landed in. (Routing guidance rides `additionalContext` → may not inject under `--print` per D14; a misfile is self-correctable, never corruption.)
- **Index composition is PLACEMENT ONLY, not frontmatter-derived and not hygiene** (CORRECTED 2026-07-14; scope narrowed 2026-07-17). `SessionStart` splices each mounted tier's `memory/<tier>/MEMORY.md` carrier into the root index as a block (global first, project bare-path last), removes a block for a tier no longer mounted, and mirrors root tier-lines back into the carrier so they propagate. That is the whole job. The agent (and CC native pointer-writing) owns each line's TEXT plus its per-file creation/deletion; composition owns only tier-block placement. Writers disjoint by ASPECT (text+per-file-presence vs tier-block-placement). Coverage/prune/dedup are REJECTED OUTRIGHT (see the 2026-07-22 presence-authority block below) — the first two contradict or invert index-authority-over-presence, the third guards a non-existent union driver.
- **Authoring-time ONE-WAY sync (index → frontmatter)** (`PreToolUse`+`PostToolUse(Write|Edit)`, CORRECTED 2026-07-15 — was "bidirectional"): mirrors an edited index one-liner's hook → frontmatter `description` (after-the-dash hook only, never `name`/title). One-way because the index is canonical — a bidi sync resolves conflicts by tool-call order (last writer wins), and since the file body is usually written after the index, the weaker frontmatter would propagate back and clobber the curated index hook (store proof: index hooks carry content frontmatter lacks — `feedback_memory_before_root_commit`, `reference_cc_worktree_memory_freeze`). `PreToolUse` captures the pre-edit index image so PostToolUse propagates ONLY the changed line(s), never a blanket sweep (which would push a stale index line onto fresh frontmatter). Frontmatter-only edits untouched; hook never writes the index. Deploys globally via plugin hooks (free per-project); complementary to the structural pass. REFINED 2026-07-16 (settled): the diff is keyed by DESTINATION path (so reordering / grouped mid-list insertion is a no-op); an ADDED line fills frontmatter only if the description is EMPTY (no overwrite — by write-order a real creation already carries its authored description, so this is a no-op there and no file-added check is needed); a CHANGED hook propagates (overwrites). See the RESOLVED block below.
- **One-time reconcile** — the semantic complement the one-way sync CAN'T do: it never fixes a stale INDEX line (harmful direction, `reference_git_hook_env_leak`), because fresher-of-two is a semantic call. Runs AFTER sync deployment (else editing re-drifts frontmatter). Per-project + once-per-shared-tier, opportunistic/lazy (optional `/gitlore:reconcile`, dogfood here), worth an explicit sweep only where a stale INDEX line bites; stale frontmatter is low-harm.

**DRIFT FINDING (2026-07-14 — refutes the earlier "frontmatter = single source of truth").** Git-history audit of THIS repo's memory: the root `MEMORY.md` one-liner and the frontmatter `description` drift BIDIRECTIONALLY — the agent only has the always-loaded root index in context, so it revises whichever surface it sees and the other rots, in *both* directions (`feedback_memory_retrieval_in_practice` = fresh index / stale frontmatter; `reference_git_hook_env_leak` = the reverse: corrected frontmatter+body, stale index line). So neither is a reliable SoT; picking the fresher of two divergent texts is a semantic call. The **index one-liner is canonical** (always-loaded + reliable retrieval lever, 100% vs 75%); frontmatter is a weaker secondary match-surface. This is *why* composition must be structural (above), not text-derivation.
- **Propagation + pinning:** SessionStart ff's the nested tier submodule(s) so cross-project global facts arrive; the recompose leaves `memory/` DIRTY — expected — and rides the next parent commit (float, but commits naturally; no scheduled sync-commit, no gate churn).
- **Conflicts:** concurrent tier-index insertions merge via the semantic memory-merger sub-agent (three-way, no diff3) — no duplication. NO `merge=union` driver (it concatenates blindly, manufacturing the duplicates a dedup would then clean). Distinct per-index namespaces bar cross-index collision. No append-only constraint; conflicts rare (more global → more stable).

**Empirical basis** for "compose into root index": interactive PTY + `--print` both confirm recall = tool-gated `Read` steered by the ROOT `MEMORY.md`; nested `team/MEMORY.md` NOT auto-loaded; index-listed → ~100% recall, unindexed → ~75%. See [[cc-memory-retrieval-agentic]].

**RESOLVED 2026-07-16 — D17 SPOT settled by eval (MemoryEval sub-agent; 528 session transcripts + a 136-file native baseline across 7 OTHER projects where gitlore's sync hook has not yet acted).** The OPEN QUESTION was: does "index one-liner canonical" cost more in AUTHORING than it wins in RETRIEVAL? Answer: **index-canonical holds, and the authoring cost dissolves once the sync stops overwriting at creation.**
- **V1 — agents curate the index hook, not the frontmatter description (≈3:1).** Post-creation Edit tool calls that actually changed a value: **40 index-hook refinements vs 14 description edits** (18 distinct files vs 7). Holds OTHERS-ONLY at 3.1:1, so it is not a gitlore artifact — it is how native auto-memory gets curated. The description is the summary agents touch *least* after birth. Confirms index-canonical on the AUTHORING side too, not just retrieval.
- **V2 — the "hook authors the index + notifies via additionalContext" reframe FAILS its precondition.** A new index line is NOT reliably end-appended: flat gitlore END=12 / MID=4 (~25% inserted mid-list, always grouped by type prefix), and sectioned indexes in other projects (candidature, edify) put the pointer list before other sections so an end-append lands in the wrong section entirely. Layout-aware placement is exactly the judgment the agent already applies → the reframe doesn't remove the agent from index authoring, only relocates the hard part.
- **Descriptions are meaningful at creation; slug descriptions do not occur.** 0/136 native descriptions are slug-like — the only real gap is the occasional MISSING description, handled by fill-if-empty. So slug-detection guards a non-existent case → REJECTED.
- **Settled sync rule (keyed by DESTINATION path, not line position):** (1) line ADDED → fill that file's `description:` only if empty, else leave it; (2) hook CHANGED for an existing destination → overwrite/propagate to the description; (3) unchanged / reordered / removed → no-op. Never a blanket sweep; never clobber a non-empty description at add-time; the write-order fact (file-with-description first, index line second) makes fill-if-empty a no-op on real creations, so NO separate file-added check is needed. REJECTED: bidirectional sync (write-order makes the index the last write, so bidi lets the weaker side win by tool-call order); slug-detection; the append/additionalContext reframe (V2).
- **Load-bearing follow-up — DONE 2026-07-16 (TDD).** The live slice-1 post-hook loop (in `scripts/cc-hooks/index-sync-post.sh`, using helpers from `scripts/lib/index-sync.sh`) previously OVERWROTE on an added line — a destination absent from the pre-image made the "unchanged?" test fail and it wrote unconditionally. Now the loop is keyed by presence-in-pre-image: an existing line propagates only when its hook changed; an **added** line (absent from the pre-image) fills `description` only when `gitlore_get_frontmatter_description` returns empty, never clobbering authored prose. 2 new `index_sync.bats` cases (added-line clobber-protection + empty-fill); `make test` 262/0. Verified LIVE this session — editing these two MEMORY.md lines fired the changed-line propagate path (additionalContext confirmed the frontmatter rewrite).

**PRESENCE-AUTHORITY SETTLED 2026-07-22 (David's call) — the INDEX is authoritative over a pointer line's presence, and the authority is NON-DESTRUCTIVE.** The index says what memory *contains*: a file on disk with no pointer line is not part of memory, and a line is added or removed only by the agent, deliberately. But authority is a *reading* rule, not a licence to make one surface match the other — **removing a line never deletes the file it named**. That would be surprising and dangerous: the file is the only place the fact still lives, and a destructive edit as the silent consequence of an index edit is the one surprise a memory store must not spring.

The direction is the opposite of the 2026-07-17 hunch (which leaned file-set-authoritative), and it **closes** the three passes deferred behind the question rather than unblocking them. **Coverage** (seed a missing line from frontmatter) contradicts the rule — an unlisted file is unlisted on purpose. **Prune** (drop a bullet whose file is gone) inverts it and destroys what may be the last trace of a lost memory; under index authority the *missing file* is the anomaly, not the line. **Dedup** was already unjustified (no `merge=union` driver). The one non-destructive addition it left open — a fifth compose validation naming a bullet whose target file is absent — is **DONE 2026-07-22** (`gitlore_compose_dangling`, 9 cases). It *reports* rather than refuses, and that asymmetry is why it is a **separate pass** called by both triggers after `gitlore_compose` returns, not a fifth rule inside `gitlore_compose_check`: the check's contract is "refuse and write nothing", and compose's return value is the list of what it WROTE (adding dangling lines to it would have broken the byte-idempotence test's `[ -z "$output" ]`, which is the signal that told me so). Because it runs after, it speaks even when composition wrote nothing — a stale line surfaces on the next index edit regardless. It scans every MOUNTED carrier as well as the root: a dormant tier's bullets never reach the root, so a root-only scan leaves them unchecked while the tier sleeps. Same-file lines in both indexes report once, against the root — the surface the agent has loaded.

**ONE MERGE POLICY AT EVERY LEVEL — DONE 2026-07-22 (500 green, 16 cases in `tests/tier_divergence.bats`).** David's framing, and it was the right one: there is one branch policy, two gates (pending-vs-local-`live` at `pre-commit`, local-`live`-vs-remote at `pre-push`), each of which can trigger `/gitlore:resolve` — and nesting changes nothing about it. Memory had both gates wired to `gitlore_yield_merge`; tiers had both gates in the right *places* but only *reported* at each ("resolving a tier divergence is not yet automated"), so a diverged tier silently stopped publishing while repeating the same message every session.

Almost nothing needed building. `gitlore_prepare_merge` / `gitlore_yield_merge` / `gitlore_write_merge_state` were already parameterized by store path, and **`gitlore_merge_state_file` resolves `--git-path` inside whichever store it is handed** — so every tier already got its own state file in its own gitdir, no collision. The single real blocker was the CONTINUATION: `load_continuation_state` derived its store from `gitlore_memory_path`, so it would have committed in memory while the prepared merge sat in a tier. Fixed by adding an absolute `store` field to the state file and having the continuation FIND the prepared merge by walking `gitlore_memory_stores` (memory, then each mounted tier, each guarded by `[ -e .../.git ]`). Two prepared merges is refused, not guessed at — a gate yields on the first divergence and stops, so two means the state is not what any continuation assumes. The memory-merger sub-agent reads `store` too: `changed_files` are relative to it, and it was previously free to assume memory.

Two defects surfaced while wiring it. The tier's local-`live` failure path had no parenthesized-reason discriminator, so a ref lock would have been sent into a merge that cannot fix it. And **`resolve.sh`'s two memory repairs (create missing remote, push missing `live`) each ended in `exit 0`** — which made a tier-divergence test pass green against a genuinely broken store, because the resolver repaired memory and returned before any tier was examined. Both now fall through: a repair to memory says nothing about the tiers.

**THE MERGE CONTINUATION COMPOSES — DONE 2026-07-22 (4 cases in `tests/resolve_compose.bats`).** Composition had two triggers, `SessionStart` and `PostToolBatch` on an index write, and a landed merge is neither: `/gitlore:resolve` synthesizes an index outside any tool edit, so a merged store stayed uncomposed until something else fired. `continue-after-merge` now composes *before* it commits (and runs the dangling report on the same pass). Three shapes: the pass is anchored at the memory ROOT, kept apart from the `store` the state file names — composition spans the whole tree while the merge sits in one store, so `load_continuation_state` yields both; it can therefore write a store OTHER than the one committed (root index when a tier merged, a carrier when memory did), and those writes stay dirty and ride the next FR11 commit, the same float SessionStart produces; and a refusal REPORTS without blocking — compose writes nothing when it refuses, and by then the merge is synthesized and approved, so stranding it half-landed over a duplicate line beats nothing. Staging is `git add -A` in the merge store, the same call the merger sub-agent already makes.

**ROOT CAUSE OF THE `04-tier-write` RATE — A MISGRADING ASSERTION, NOT THE AGENT (2026-07-23).** The hypothesis above ("the agent-side half of FR11 is unreliable") was wrong, and the way it was disproved is the lesson: an absent commit-msg file had been read as "the agent never wrote the summary", but that state has TWO causes and the assertion assumed the losing one. FR11 gives the agent two equally-correct finishes once the user approves — write the summary and STOP (the next parent commit consumes it), or write the summary AND the trigger, which makes `memory-commit-batch.sh` commit *during the agent's own session* (the documented standalone path, and the only one a session with no pending parent commit can take). The old `tier-write.sh` asserted `[ -f "$MSG_FILE" ]`, i.e. it accepted ONLY the stop path and failed every trial where the agent took the batch path — where the file is correctly already consumed and memory has already advanced. So the "flakiness" was the agent nondeterministically choosing between two correct finishes, and the assertion only liking one. Fix: grade the OUTCOME, not the stop-point — establish which path ran (msg-file present → fire the parent commit; absent but memory moved → the hook already did it; absent and memory unmoved → a real miss, and name whether the trigger is parked), then assert the same end state either way (both stores advanced, tier HEAD contains the fact, gitlink lockstep, both at `live`, summary consumed, rubric). The discriminator that cracked it: when an assertion can fail for opposite reasons, make its message report which one actually happened ("memory ALREADY moved $before -> $after" vs "trigger present, no summary" vs "nothing moved") — one `git rev-parse HEAD` against the captured baseline told stop-path from batch-path from genuine-miss in one run. After the fix `04-tier-write` is **5/5 in isolation**. The eval-assertion suite (`tests/evals/lib/asserts.bats`) now covers both finishes plus the one-behind-gitlink lag; the fixture had to wire the parent `pre-commit` hook (via `emit-wrappers.sh` + `git config gitlore.hooksDir`) since `_make_memory` builds the submodule without hooks, so the stop path's `git commit` was previously inert.
