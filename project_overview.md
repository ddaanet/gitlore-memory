gitlore is a Claude Code plugin that makes Claude's auto-memory system versioned, shared, and git-backed. Memory lives in a git submodule inside the project repo, synchronized across worktrees via a local `live` trunk branch.

**Why:** Replace the default per-machine `~/.claude/projects/<hash>/memory/` with a tracked, pushable, multi-session memory store.

**Plan 06 superseded → D11 design (2026-05-25):** executing Plan 06 (worktree lifecycle) surfaced a deeper flaw, verified empirically against git 2.47.3: gitlore's hook wrappers hardcoded the relative path `.git/gitlore-<hook>`, which only resolves when `.git` is a directory. In a linked worktree `.git` is a gitlink *file*, so the write aborts SessionStart and the shared wired hook's `exec` **blocks the commit outright** — linked worktrees were unusable at a more basic level than "memory missing." Fix is **D11** (in `docs/design.md`, commit `98f1511`): anchor wrappers at `$(git rev-parse --git-common-dir)/gitlore-<hook>` (shared across worktrees) on both write and exec sides, across **all five** hook managers (direct via `--git-path hooks/<hook>`; husky `exec`; lefthook `run:`; overcommit `sh -c` array; manual). Plus early `[ -e "$mempath/.git" ] || exit 0` guards in `pre-commit`/`pre-push`. Plan 06's two deliverables (SessionStart memory-worktree creation; advisory `WorktreeRemove`) are absorbed. The old Plan-06 file (`docs/plans/2026-05-25-06-worktree-lifecycle.md`, `de1fc93`) is **stale** — do not execute it.

**Next release adopts the `claude-plugin-dev` release toolkit (2026-05-26):** `ddaanet/claude-plugin-dev` (`~/code/claude-plugin-dev`) is a toolkit *vendored into a consumer plugin via `git subtree --prefix=plugin-dev`* (pin to a `vX.Y.Z` tag), NOT a marketplace. It provides: `release.just` (imported into the consumer's `justfile`; its `release {patch|minor|major}` recipe bumps `.claude-plugin/plugin.json`, commits, tags `vX.Y.Z`, pushes, `gh release create --generate-notes`), `version-guard.sh` (a `PreToolUse(Write|Edit)` hook refusing manual edits to `plugin.json`'s `.version` — the recipe owns bumps), and `install.sh` (wires the justfile `import` line + the hook into `.claude/settings.json`; idempotent). Integration = `git subtree add --prefix=plugin-dev <url> <tag> --squash`, then add a gitlore `justfile` with a `precommit` recipe (the `release` recipe depends on it — wrap `make test` + `make check-version`), then run `install.sh`. This replaces the current manual release flow (hand-bump + `/plugin marketplace update`) and finally gives gitlore git tags. **It does NOT subsume `scripts/check-version.sh`** — the toolkit guards `plugin.json`↔git-tag; `check-version.sh` guards `plugin.json`↔the separate `marketplace.json` ([[feedback_preflight_stays_generic]]). Open: the toolkit's recipe bumps `plugin.json` + tags but is unaware of the marketplace repo, so the marketplace.json bump + `/plugin marketplace update` cache-bust ([[reference_plugin_cache_staleness]]) still needs handling alongside it.

**Toolkit integrated; release pending the `just release` run (2026-05-26):** `claude-plugin-dev` is now vendored at `plugin-dev/` (subtree, tag `v0.2.0`); gitlore has a `justfile` (`import 'plugin-dev/release.just'` + a `precommit` recipe = `make check-version` + `make test`); the `version-guard` `PreToolUse(Write|Edit)` hook is wired into `.claude/settings.json`; `.envrc` exports `MARKETPLACE_DIR=$PWD/../claude-plugins`. **Correction to the paragraph above:** the v0.2.0 recipe IS marketplace-aware — it bumps + pushes the `marketplace.json` entry via `$MARKETPLACE_DIR`, so that step is no longer manual (only `/plugin marketplace update` cache-bust remains). The release itself is **not yet run**: `env MARKETPLACE_DIR=$PWD/../claude-plugins just release minor --yes` bumps `0.1.1`→`0.2.0`. gitlore has **no git tags yet**, so the first release skips the recipe's tag-match guard. **Classifier gotcha:** in auto mode the subtree add, running `install.sh`, the settings.json hook edit, and all cross-repo/submodule pushes are denied as external-integration / self-modification / cross-repo — they must be run by the user via `!` (see [[reference_cross_repo_push_auth]], [[feedback_memory_before_root_commit]]).

**Hooks now wired here + detection default changed (2026-05-29, released `0.2.3`):** The prior "don't chase" gotcha is resolved — we wired the hook in this repo. Root cause was broader than this repo: `detect.sh` emitted `direct` only when an executable `.git/hooks/pre-commit` already existed, so a no-manager repo (this one — gitmoji installed only `commit-msg`) fell through to `manual`, which wires nothing — the `pre-push` double-commit hook silently never fired, so `just release`'s `git push` never pushed the memory submodule. Fix (commit `75f46df`, in `0.2.3`): detection now defaults the no-manager case to `direct`; `manual` stays a hand-set sentinel + the multi-manager fallback. This repo wired via `wire-direct.sh` (`.git/hooks/{pre-commit,pre-push}` exec the common-dir wrappers; sentinel `manual`→`direct`). The latent `live`/`main` drift (memory `live` frozen at "Initial memory" while real history lived on `main`/`origin/main`) was reconciled: ff `live`→`main` (`9ba042a`), both pushed; now fully converged. **The pre-commit/pre-push machinery is live in this repo going forward** — memory commits here now flow through the wired hooks (pre-commit will block a parent commit if memory is dirty without an approved summary), not pure manual management.
